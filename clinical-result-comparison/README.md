# Clinical Result Comparison

Tool Smith project assets for source-grounded synthesis and comparison of multiple selected clinical result records. The default output is a trial-level evidence synthesis for same-trial selections and a comparison-first, domain-aligned cross-trial comparison for mixed selections, each with a compatible chart when the data allow it.

## R49 + R50 — one delivery per value, an appendix that is a table, and a report that never narrates itself (published in place, five live runs)

Prompt **v0.16** and the Skill bundle changed again, **in place** (labels v1.7 / v1.0.8 unchanged), from five defects the user found in the delivered report: four layout/duplication complaints (R49) and one register complaint (R50) — *"the report contains the model's own reasoning: `**分析模式：** 跨试验、非头对头…`, `**可比性结论：** 可绘图.`"* — with the instruction to sweep the whole report for that register, fix it, republish in place and test again.

- **R49.1 — the appendix opens with its table, not with a specification.** `render-facts.py` dropped `APPENDIX_INTRO` (≈600 characters of "how this table is laid out") and keeps a one-line `APPENDIX_LEGEND` for `—`. `check_report.py` now FAILs on a prose block > 100 characters between the appendix title and its table, and on the appendix title appearing more than once (a hand-written appendix next to the rendered one). The four templates state that the renderer owns title / legend / columns.
- **R49.2 — appendix column headers.** A single trial with ≥ 2 disclosures now reads `**readable label**<br>ref_n` (falling back to `**ref_n**`), and a registry number already present in the display name is no longer repeated on the second header line.
- **R49.3 — one delivery per value (option 1: keep every chart, drop the repetition).** The institutional source was §二 of the two summary templates prescribing a table *and* a chart in the same section. `check_report.py` adds two FAIL rules — chart prose (`subTitle` / `describe` / `data[].description`) restating its own plotted value, and a non-appendix section carrying a chart *plus* a table that repeats ≥ 2 of that chart's plotted values (dose / interval / time-point / count digits and study-internal control or boundary values stay allowed; the appendix and timeline charts are exempt). Both templates now say "do not repeat the table after the chart" instead of "keep the table".
- **R49.4 — four speed levers that do not trade away quality**: the `references/toolbox.md` FAQ (so the model stops reading the packaged scripts' source), a prompt rule against re-reading its own files plus a single `check_report.py` pass, `build_ledger.py --scaffold` (candidate fact rows straight from the raw payloads; it never writes `ledger.json`), and one-shot chart specs. The bottleneck was rule density → hidden reasoning, so acceptance is measured on output / reasoning tokens and wall clock.
- **R50 — the fourth forbidden register: the report must not narrate itself.** None of the existing guards (`A-P1` coverage line, `op_original_check_names_class`, `A-P5`, `A-P7` template-spec echo, `A-P8` rule metastatement, `A-P10` run logistics) covers *the report describing its own method, classes or process*, which is exactly what the user saw. `check_report.py` gained a `report voice` group (six regexes + `_meta_narration_findings()`) and **`check.py` was deliberately left alone** so the 44/12 mutation suite keeps its meaning. **FAIL**: self-labelled bullets or table columns (`分析模式` / `选择依据` / `可比性结论` / `对齐等级` / `不绘图原因` / `有限并列原因` / `纳入标准` / `检索策略` / `报告结构`), our own work presented as a class (`可绘图` / `只能有限并列` / `不具备绘图条件` / `部分对齐` / `仅背景对齐`), process phrases (`本次选择` / `本次纳入` / `我们选择` / `本轮`), internal or runtime vocabulary (`src=` / `esid` / `payload` / `JSONL` / `MCP` / `工作区` / `沙箱`) and self-audit tails (`无未复核记录` / `无遗漏` / `全部通过`). **WARN**: broad self-reference (`本报告` / `本次`, with a negative lookahead keeping the legitimate `本次披露`). `比较口径` is deliberately *not* failed (every template legitimately carries that blockquote), and `token` / `轮次` are not blanket-banned (they would hit *treatment cycle*). The rule is written once in `SKILL.md`, in the prompt's pre-delivery checklist and in `references/toolbox.md` (§7 + two FAQ entries), and the four templates lost their `分析模式` / `选择依据` / `对齐等级` labels — the differences are stated as time-point / population / definition / direction instead.

## Product boundary

- Input is delivered as a **selected esid list**: the frontend sends each selected clinical result as its clinical-result esid (`clinical_result.extra_esid`) in the user turn. The Agent pulls the detail records itself through the MCP tool `pharmcube-query-clinical-result-with-params`, passing `esids` plus a strict, minimal `selected_fields` allowlist (names copied verbatim from the live tool schema; `docs/params-tool-schema.md` is a maintainer mirror). Clinical evidence comes from the pulled clinical-content fields (`abstract_text`, `summary`, `study_results`, design/arms context); `paper_title`, `full_article_link`, `paper_release_time` are citation metadata; entity fields (`projects.associate_ids`, `trial_abbreviation`, `arms[].drugs[].drug_earth_id`, `projects.company_ids`) are display/label metadata for inline entity references only.
- The backend/frontend supply only the selected esids. The Agent never invents IDs or adds unselected records; it may retrieve original sources for those records within the routes and budgets in `references/input-contract.md`. Runtime identifiers and retrieval/storage details remain outside the Agent request and report.
- Per-esid mapping keeps large selections (20–50 results) addressable; a strict `selected_fields` set bounds the returned payload (a full record or a huge response can exceed the context budget). Input (esid) order defines `{{ref_n}}` assignment. Input order is a presentation label, not clinical chronology.
- Runtime identifiers and retrieval/storage details remain outside the Agent request and report.
- The primary analysis object is the underlying trial. Multiple disclosures from one trial are source nodes that are deduplicated into a longitudinal evidence chain covering design, efficacy, safety, maturity, and information gaps.
- Every material number and source-dependent conclusion carries an internal citation token for rendering; the user-facing report shows numeric superscripts. Citation metadata is emitted separately as strict JSON, with `title`, `link`, and `paper_release_time_str` per ref.
- For mixed inputs containing different trials, the deliverable is comparison-first and domain-aligned: efficacy, safety, PK/PD, and PRO are aligned across trials so the user can judge which treatment is better or worse, with explicit comparability/evidence-strength labels and compact per-trial context. The report does not pool results or fabricate head-to-head proof. `{{ref_n}}` numbering is global across the complete response and the separate citation JSON is shared; numbering resets only when the runtime explicitly requests separate independent reports.
- The L3 evidence policy analyzes the deepest retrieved source for each selected record, declares coverage/depth, and points full-text citations to the fetched carrier under the input contract. HTTP 500 or a missing PMCID alone does not establish non-OA status. `clinical_result.group_count` means enrollment, not arm count.
- The frontend may render each marker as a numeric superscript link using the final JSON. Supplied URLs stay exact except for the documented fetched-full-text citation rule; rendering must use safe external-link attributes.
- The backend/frontend enforce a conservative real-time token budget.

### Publishing without the web UI (personal-token API, verified 2026-09-11)

Prompts and Skill archives can be published from a script instead of the Web pages, through the ToolSmith personal-token API (`<host>/docs/integrate/token-api`) on the same instance that serves the chat shares. Authenticate with a personal access token (a `ts_pat_`-prefixed string created under the user menu → 「访问令牌」) sent as an `Authorization: Bearer …` header; keep it in the environment (`TS_BASE`, `TS_TOKEN`) and never commit it.

- Deployed identities: prompt family `91febc286412479a8b6d569fa3b8025e`, Skill family `9fe0035bdd324b998436c6cb9c2de212`, project `a7cdda6508e0423c8b7afaaf3a68e50d`. The project binds the prompt **version** and the Skill **family**, so publishing a new version is enough — no project edit.
- Append a prompt version: `POST /api/prompts/{family_id}/versions` with `{version, content, ifadd: true, is_current: true}`. A duplicate label in the family is rejected; the new version becomes current automatically.
- Append a Skill version: `POST /api/skills/create` (multipart `name`, `version`, `file`, plus `family_id` and a non-empty `message`), the same call that creates a brand-new Skill. `name` must equal the `SKILL.md` `name`. The new version becomes current and demotes its predecessor. `POST /api/skills/update_skill_file` is **not** this path — it overwrites the files of one existing version (`commit_id + 1`) and creates no history.
- Platform version labels are their own sequence (prompt `1.x`, Skill `1.0.x`) and are mapped to the repo's `v0.x` names by content hash, so `status` prints that mapping instead of guessing.
- The whole flow is wrapped by the global command `toolsmith-publish` (`~/.local/bin/`, outside this repo; per-project ids live in `~/.config/toolsmith/projects.json`, credentials in `~/.secrets`). `status` is read-only and exits 3 when the deployment and the worktree disagree; `publish` updates the current prompt and Skill versions in place and re-verifies; `--new-version` explicitly appends versions. Nothing here is hardcoded in the repository.

### Self-verification after each iteration (verified 2026-09-13)

After touching `skill/` or `system-prompts/`, run one real chat turn through the API and assert on its outputs:
`toolsmith-publish run --prompt-file ~/.local/state/toolsmith-runs/ask.txt --tag <tag>`. It opens a thread, posts one user message, reads the SSE stream only far enough to see
`data-turn-start` (<=20 s) and then disconnects, and polls `GET /api/threads/{tid}/info` (`status`) every <=60 s for the terminal state
(the platform runs the turn as an independent task, so a detached client does not cancel it). It then collects `/timing`, `/usage`, `/info`,
`/artifacts/archive` (whole-workspace zip), `/messages` and `/debug/history`, writing a
`verification.md` plus a human-readable `transcript.md` into `~/.local/state/toolsmith-runs/<ts>-<tag>/`. A `run.json` with the
`thread_id`/`turn_id` is written *before* the POST, so `--resume <THREAD_ID>` can pick a run back up; a repeated POST returns `409` and is
treated as idempotent (never re-POST after a timeout). `--resume` writes a **new** run directory by default (the original record stays frozen; pass
`--out` only if you really mean to overwrite). `--web` sends `enable_web: true` in the turn body so a run can
actually exercise the platform's Web tools (`web_search`/`web_fetch`): the platform gates them on *project capability AND the
per-request flag*, and the flag was hard-coded `false` here (ledger O18), so no run could ever reach that path. Since the platform's `30306cb` (2026-09-16) `/info.status` is a hard
`preparing | running | cancelling | idle` vocabulary — the terminal values were **removed from the API** and a finished run leaves memory
immediately (P7 fixed at the root) — so `idle` means "no live run here", never a verdict: the run is closed from the **durable**
`/timing` row instead, `completed_at` present ⇒ `completed` (annotated with where it came from); a run that goes live and then vanishes
with no DB row (process restart) is called `inconclusive` at once instead of burning the whole `--timeout`. Outcome is likewise no longer
in `/info` (there is no outcome field anywhere, and no outcome column in `thread_messages`), so `classify_outcome()` reads the persisted
messages the platform already normalises — a part with a top-level `error_type` (`stream_error` / `TimeoutError` / exception name) means
`failed`, `state="interrupted"` or a `Cancel`-ish error type means `cancelled`, no messages at all means `unknown` — and a turn the
platform silently failed is no longer reported as `completed` (assertion #17).
Exit codes: `0` all assertions passed, `3` ran but something failed,
`4` the turn never landed in the database (`not_started`), `5` no live terminal state *and* no `completed_at` in the DB row (`inconclusive`), or polling timed out.
The tool chain and every error are rebuilt from persisted messages, not from SSE; a call rejected by a tool schema is reported separately
as `args-refused` rather than as a tool error. External retrieval failures are visible as `fetch-failed`; unexplained missing returns fail. Final target-turn messages, not poll observations, define required receipts; on-disk bytes and hashes must match, and ambiguous ownership fails closed. Assertions cover the deployed bytes (system prompt == local `system-prompts/*-v*.md`; skill body == local
`SKILL.md`; the supporting-file manifest matches file by file) and the output contract (fixed artifact paths, chart file names,
envelope keys/`id`/`iframe_template`/`type`, `::visualization` tag count, leftover placeholders, nested entity anchors,
`{{ref_n}}` closure, citations keys plus a date-only `paper_release_time_str` and a non-empty `title` per entry, `present_artifact` last,
no tool errors). Findings are logged in `docs/toolsmith-verification-log.md`
(one `R<n>` entry per run, plus the two-column list "what we can fix" / "platform issues for the developers").
Platform issues intended for other people are kept outside this repo (in the user's Obsidian vault).
A run creates a thread, so it passes the same ownership guard as publishing.

### Offline fact-check scorer (`evals/fact-check/`)

`run` only proves the contract holds; it cannot tell a good report from an empty-but-well-formed one. `evals/fact-check/` adds the
missing quality scalar: `records/*.json` hold the ground truth captured from `POST /api/tools/debug`, `scenario-{a,b}.facts.json` list the
facts a run must state (**43 A + 12 B** `fail`-level items, one `warn`-level each, evaluator `2026-09-18-r2`), and `check.py` scores a run directory completely offline:

```bash
python3 evals/fact-check/check.py --run ~/.local/state/toolsmith-runs/<ts>-<tag> --scenario a
# SCORE scenario=a facts 43/43 warn 1/1 -> PASS          (exit 0 pass / 3 fail / 4 unusable input)
python3 evals/fact-check/mutations.py                    # negative control: proves every item can go FAIL
```

Checklists are written from the recorded tool responses *before* any product is inspected, so a report can never certify itself;
*(2026-10-10 update: scenario A is now **45 items / 44 fail**, `mutations.py` applies **64** controls — see the current snapshot above; the paragraph below is the 2026-09-18 snapshot.)* `mutations.py` applies 63 controls to real-run copies: 42 A failure mutations, 14 B failure mutations, and 7 must-remain-clean controls. Missing baselines fail rather than silently skipping checks. Full-text evidence checks establish archived body/source identity, not that every reported number was extracted from it.
See `evals/fact-check/README.md` for the item kinds and the known gaps (the deployed-vs-online `iframe_template` equality is only
checked by the online `run`, and v1 SSE run directories are reconstructed from `debug-history.json`).
