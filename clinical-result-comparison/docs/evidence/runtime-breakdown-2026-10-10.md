# 一次 run 的墙钟时间都花在哪（2026-10-10，只读分析）

数据来源：`~/.local/state/toolsmith-runs/<run>/` 的 `timing.json` / `usage.json` /
`debug-history.json`（`raw_model_messages` 里每次 request / response 的 `timestamp`、
`usage.output_tokens`、`details.reasoning_tokens`，工具返回各自带 `timestamp`）。
分析脚本：`/tmp/timing/{analyze.py,timeline.py,regress.py,volume.py,split.py,table.py}`。
**本轮只读，未改任何资产、未新增 run。**

## 1. 结论先说

1. **run 时长的一半以上是模型在"写字"，不是工具慢、不是查询慢。**
   把每一步的 `response → 下一个 request` 间隔对**该步输出 token 数**做回归，
   8 个 run 的 R² 全在 0.95–0.99：

   | run | 回归式（gap = a + b·out_tokens） | 生成占比 | 每步固定开销（工具+往返） |
   |---|---|---|---|
   | r46-a | 1.49 s + 4.0 ms/token (R²=0.97) | 78% | 52 s (16%) |
   | r46-a2 | 1.42 s + 3.7 ms/token (R²=0.96) | 84% | 40 s (11%) |
   | r45-a | 1.50 s + 3.7 ms/token (R²=0.98) | 78% | 54 s (16%) |
   | r45-4 | 1.72 s + 3.5 ms/token (R²=0.99) | 78% | 64 s (16%) |
   | r45-18 | 2.15 s + 3.3 ms/token (R²=0.97) | 68% | 103 s (25%) |
   | r45-14 | 2.19 s + 3.3 ms/token (R²=0.95) | 75% | 118 s (19%) |
   | r44-a | 1.65 s + 4.1 ms/token (R²=0.97) | 79% | 77 s (16%) |
   | r44-18 | 2.57 s + 3.3 ms/token (R²=0.97) | 65% | 180 s (27%) |

   ⇒ 解码速率约 **250–300 output token/s**（3.3–4.1 ms/token）；
   固定项 **1.4–2.6 s/步**（工具执行 + provider 往返 + 采样开销）。

2. **生成里的大头是"想"，不是"写"：reasoning 占全部输出 token 的 46%–76%。**

   | run | 墙钟 | 步数 | out_tok | 其中 reasoning | 生成估算 | 生成占比 |
   |---|---|---|---|---|---|---|
   | r46-a | 330 s | 36 | 64,845 | 45,533 (70%) | ~259 s | 79% |
   | r46-a2 | 361 s | 29 | 82,044 | 46,337 (56%) | ~328 s | 91% |
   | r45-a | 344 s | 37 | 71,842 | 49,868 (69%) | ~287 s | 83% |
   | r45-4 | 390 s | 38 | 87,305 | 55,364 (63%) | ~349 s | 89% |
   | r45-18 | 411 s | 49 | 84,159 | 45,775 (54%) | ~337 s | 82% |
   | r45-14 | 627 s | 55 | 143,737 | 65,973 (46%) | ~575 s | 92% |
   | r44-18 | 655 s | 71 | 128,188 | 82,096 (64%) | ~513 s | 78% |
   | r43-4 | 499 s | 53 | 97,103 | 73,357 (76%) | ~388 s | 78% |

   ⇒ **reasoning 一项就吃掉 180–330 s**（45k–82k token × ~4 ms）。

3. **工具本身很便宜。** 一批工具调用里第 2 个起的"纯工具时间"实测：
   `read_file` 0.2–3 s/次、`grep`/`ls` <1 s、`pharmcube-query-clinical-result-with-params`
   1–9 s、`execute`（跑自产 Python 渲染/校验）2–8 s，`load_skill` <1 s。
   一次 run 全部工具时间加起来约 **30–80 s（<15%）**。数据库查询与渲染都不是瓶颈。

4. **单步最大的开销是"一次 write_file 生成 12k–36k token"**：
   r45-4 有一步 35,864 token = 129 s；r45-14 有一步 17,046 token = 71 s；
   r44-18 一步 26,245 token = 78 s。也就是**报告/账本/脚本的正文本身就是时间**。

## 2. 记录条数与耗时的关系：几乎无关

| 输入 | run | 墙钟 |
|---|---|---|
| 2 条 esid（场景 A） | r46-a / r46-a2 / r45-a / r44-a / r43-a / r41-fixed-a | 330 / 361 / 344 / 495 / 384 / 353 s |
| 4 条 esid | r45-4 / r44-4 / r43-4 | 390 / 381 / 499 s |
| 14 条 esid | r45-14 / r44-14 / r43-14 | 627 / 512 / 492 s |
| 18 条 esid | r45-18 / r44-18 / r43-18 | 411 / 655 / 503 s |

⇒ **2 条记录和 18 条记录的耗时是同一量级**（都在 5–11 分钟）。
耗时不是"取回/查询"成本，而是**固定交付成本**：不管几条记录，都要产出
正文 + 精确值表 + 附录 + 图表 JSON + citations + 账本 + 自检，每一步都要重新过一次上下文。
所以"2–3 个结果也要 5 分钟+"属于当前流水线的预期值，不是异常。

## 3. 时间到底被哪些产物吃掉（实测生成量）

每 run 由模型自己写出的文件正文（`write_file` 的 `content` 长度合计）：

| run | 写出的字符数 | ≈ token | ≈ 时间 | 主要产物 |
|---|---|---|---|---|
| r46-a | 32,328 | 9.5k | ~36 s | `work/draft.md` 13.2 KB、`scripts/make_ledger.py` 8.0 KB、4 个辅助脚本 |
| r46-a2 | 63,212 | 18.6k | ~71 s | `scripts/build_all.py` **63 KB 单文件** |
| r45-a | 34,485 | 10.1k | ~39 s | `scripts/build_inputs.py` 14.3 KB、`work/draft.md` 14.1 KB |
| r45-4 | 51,341 | 15.1k | ~57 s | `scripts/build_ledger.py` 24.1 KB、`work/draft.md` 20.9 KB |
| r45-18 | 59,720 | 17.6k | ~67 s | `scripts/build_ledger.py` 39.3 KB、`work/draft.md` 20.4 KB |
| r45-14 | **133,848** | 39.4k | **~150 s** | `work/draft.md` **89.5 KB**、`make_ledger.py` 24.4 KB、7 个脚本 |
| r44-18 | 70,161 | 20.6k | ~78 s | `build_ledger.py` 30.5 KB、`draft.md` 22.8 KB、5 个脚本 |
| r44-a | 37,297 | 11.0k | ~42 s | 6 个脚本（`gen_draft.py` 15.7 KB …） |

两条稳定模式：

- **模型每次都在现场手写"构账本 / 生成 citations / 画图 / 校验"的 Python 脚本**，
  单文件 8–63 KB；这些脚本的正文就是纯粹被烧掉的生成时间与 token。
- **先写 `work/draft.md`（13–89 KB）再成文**，等于把最终报告生成两遍。

其余生成量（约 25–50%）花在**短工具参数 + 推理 + 收尾文本**上。
