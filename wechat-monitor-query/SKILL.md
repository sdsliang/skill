# 公众号采集查询（按公众号名称）

> 用户给你一个**公众号名称**，你回答它在这套微信采集系统里**是什么状态**。
> 数据源是「公众号采集运行台」的 HTTP JSON API，**只读、无需鉴权**。
> 除了接口本身，下面每条判定规则都是实测出来的，**不要凭常识改**。

## 0. 输入与边界

- 输入 **只有一种**：公众号名称（如 `核言阅舍`、`纪源资本`）。用户可能写错字、少字、带全角符号。
- 不要要求用户给 URL / 文章标题 / id —— 那不是这个 skill 的活。
- **本 skill 只读**：只发 `GET`。不要尝试改采集配置、补标识、重排队列；这些只作为「建议」写进回答，由人去做。

## 1. 接口（唯一数据源）

```bash
BASE=${WECHAT_MONITOR_BASE:-http://monitor.spider.drugcube.com:8383}
```

| 用途 | 请求 |
|---|---|
| 按名字找号 | `GET $BASE/api/accounts?q=<名字>&enabled=all&page_size=20` |
| 单号详情（含近 7 天日表 + 最近任务） | `GET $BASE/api/accounts/<id>` |
| **该号已采集文章（权威口径）** | `GET $BASE/api/articles?account_id=<id>&page_size=1` |
| 全站总览（在线/积压/覆盖率） | `GET $BASE/api/overview` |
| 探活 | `GET $BASE/api/health` |

```bash
curl -sS -m 15 --get --data-urlencode 'q=核言阅舍' \
  --data 'enabled=all' --data 'page_size=20' "$BASE/api/accounts"
curl -sS -m 15 --get --data 'account_id=61721' --data 'page_size=1' "$BASE/api/articles"
```

必须注意的接口语义（实测，别猜）：

1. **`q` 是子串/分词匹配，不是精确匹配、没有模糊纠错**。`言阅舍` 能命中 `核言阅舍`；名字写错一个字（`核言阅舍色`）就是 `total=0`。
2. **不传 `enabled` 时后台默认只返回「已启用」账号**。查不到不代表不在名单里 —— **一律显式带 `enabled=all`**。
3. 响应是 `{"total": n, "items": [...]}`；`items` 里的行已经带 `status_label` / `queue_label` / `delay_label` / `consecutive_failures` / `fetch_error` / `collect_enabled`，够做初判；要日表/任务明细才再请求 `/api/accounts/<id>`。
4. **`page_size` 最多用它默认或 ≤20**。这里不是给你翻页捞数据的；只要判定结论，不要大分页。
5. **统计「这个号采了多少篇」必须用 `/api/articles?account_id=<id>`，不能用 `q=<名字>`。** `/api/articles` 的 `account_id` 参数就是账号 id（等于文章行里的 `target_id`）；而 `q=<名字>` 是模糊匹配会**串号**（实测：`q=医学界` → 25760 篇，`account_id=34316` → 实际 1665 篇）。
6. **`/api/articles?account_id=<id>` 返回按 `discovered_at` 倒序**，所以 `page_size=1` 拿到的第一条就是**最晚发现的那篇**，`total` 不受 `page_size` 影响 —— 拿「共采集多少篇 + 最晚发现时间」只要 1 次小请求。
7. **不要用 `/api/accounts/<id>` 里的 `last_new_article_at` / `today_inserted_count` 当文章统计**：实测有号的这些字段是 `null`/0，而文章库里明明有几十篇。文章数一律以 `/api/articles?account_id=` 的 `total` 为准。
8. 接口不可达（超时/连不上）= **如实说「监控台暂时连不上」**，不要编状态，也不要退回用别的方式猜。

## 2. 查询流程

```
取用户给的名称 → 清洗（去全角符号/空格，只留中英文数字）
  └─ GET /api/accounts?q=<清洗后>&enabled=all&page_size=20
       ├─ 有行且存在 name 完全等于清洗后的 → 就用它（唯一命中）
       ├─ total==1（名字略有差异）→ 就用它，但回答里注明「按最接近的命中处理」
       ├─ total>1 且无完全同名 → 歧义：按最长公共子串排序取前 3，列给用户让他指定，**不要自己挑**
       └─ total==0 → 见 §3 名字写错时的降级探测
```

拿到目标号后：

1. `GET /api/accounts/<id>`（详情，拿 `daily` / `recent_tasks`）。
2. **`GET /api/articles?account_id=<id>&page_size=1`** —— 拿「共采集多少篇」(`total`) + 「最晚发现时间」(`items[0].discovered_at`)，顺带可以给出最新一篇标题。若 `total==0` 就报「未采集到任何文章」。（**不要用 `q=<号名>` 代替**，会串号。）
3. **只有当这个号被判为「不健康」时**，再 `GET /api/overview` 看 `collector.online` —— 用来区分「这个号自己有毛病」和「全站采集器挂了」。

## 3. 名字写错 / 写不全时的降级探测

`total==0` 时不要直接说「不在名单里」，先降级找候选：

1. 把清洗后的串切 **3-gram、2-gram**（如 `言阅舍色` → `言阅舍`/`阅舍色`/`言阅`/`阅舍`/`舍色`）。
2. 每个 gram 最多取前 6 个，逐个 `GET /api/accounts?q=<gram>&enabled=all&page_size=20`。
3. 候选打分 = `命中gram数 × 10 + 与输入的最长公共子串长度`；**只保留公共子串 ≥ max(2, min(4, ceil(输入长度×0.4)))** 的候选，防噪声。
4. 输出：「「X」不在监控名单里 / 可能你要找的是：A、B」，**并要求用户用完整名字重发一次再出正式结论**。

不要做的事：不要把候选直接当成答案给完整诊断（名字错一个字可能是完全另一个号）。

## 4. 判定规则（核心）

### 4.1 该号的问题项

| 条件 | 问题 | 根因含义 |
|---|---|---|
| `alias` 和 `biz_username` **都为空** | 缺标识 | 采集器解不出 `fakeid`，**这是最硬的根因**，通常伴随 `fetch_error=book_id_decode_failed:fakeid_missing` |
| `collect_enabled` 为 false | 采集开关已关闭 | 号被停采 |
| `consecutive_failures ≥ 3` | 连续失败 | 可能被风控 / 接口变更 / 号已改名注销 |
| `last_success_at` 为空 | 从未采集成功 | 与缺标识强相关 |
| `delay_seconds > 0` | 任务积压 | 看是全站性还是单号 |
| `fetch_error` 非空 | 采集报错 | 原样引用报错串，别翻译成别的 |

### 4.2 健康度分级（顺序判定，先命中先取）

| 级别 | 触发 | 给用户的说法 |
|---|---|---|
| `broken` 已停摆 | 缺标识 / 采集开关已关闭 / 有 `fetch_error` /（从未成功 且 连续失败≥3） | 「在监控名单内，但**采集已停摆**」 |
| `failing` 采集失败 | 连续失败≥3 或 从未成功 | 「在名单内，但**一直在失败**」 |
| `delayed` 积压延迟 | 只有 `delay_seconds>0` | 「名单内，采集正常，只是**积压延迟**」 |
| `ok` 正常 | 以上都不满足 | 「名单内，采集**正常**」 |

**`delayed` 且 `collector.online == false` 时，必须改说法**：`积压延迟（全站性 · 采集器离线）`，并明确告诉用户「**这个号自身没问题**，是全站采集器挂了导致的」。
> 实测坑：采集器离线时全站所有号都会显示 `delayed`，很容易被误报成「这个号坏了」。**必须做这一步区分。**

### 4.3 常见结论 → 建议动作（一一对应）

- 缺标识 → 「补全 `alias`/`biz_username`（待补全标识流程）后重新入队」；若同时有 `book_id_decode_failed:fakeid_missing`，说明**报错和缺标识是同一个原因**，不要当成两个问题报。
- 采集开关已关闭 → 「该号采集开关被关，需要时在后台重新启用」。
- 其他 `fetch_error` → 「报错 `<err>` 需交采集器侧排查」。
- 无标识却连续失败 → 「排查是否被风控 / 接口变更」。
- 无标识却从未成功 → 「检查该号是否已注销或改名」。
- 只有积压 → 按 §4.2 区分全站性/单号，给对应说法。
- 无问题 → 「无需动作，采集正常」。**不要为了凑内容硬塞建议。**

## 5. 输出格式（回答里就这么写）

**第一行必须是「公众号名 + 结论」**，人扫一眼就知道结果。

### 5.1 不健康（已停摆 / 采集失败 / 积压延迟）

```
【<公众号名>】采集查询
结论：<在监控名单内 · 采集已停摆（33 天没采动）/ 一直在失败 / 积压延迟 4.7 小时>
根因：<唯一源头，如：缺 alias/biz_username → 采集器解不出 fakeid（book_id_decode_failed:fakeid_missing）>
· id <id> · <队列> · <频率> · <来源> · 采集开关 <开/关>
· 共采集 <total> 篇 · 最晚发现 <discovered_at，到分钟>
· 上次成功 <时间/从未> · 上次尝试 <时间> · 连续失败 <n>
建议：<1~2 条>
```

### 5.2 正常

```
【<公众号名>】采集查询
结论：在监控名单内 · 采集正常
· id <id> · <队列> · <频率> · <来源> · 采集开关 开
· 共采集 <total> 篇 · 最晚发现 <discovered_at，到分钟>
· 上次成功 <时间>
```

> 正常号**不写**「根因」和「建议」两行（无问题可报）——「无需动作」这种话也不用说。

### 5.3 填写规则

- **「根因」只写一条**，取问题项里的源头，优先级：缺标识 > 采集开关已关闭 > 其他 `fetch_error`。其余问题**不并列**；需要体现就当括号里的表现接在后面（如 `→ 连续失败 25 次`）。
  > 反例（别这么写）：把「缺标识；采集报错 fakeid_missing；连续失败 25；从未成功；任务积压」5 条平铺成一行 —— 它们是一条因果链，不是 5 个毛病。
- **「延迟」只出现在结论里**（`采集已停摆（33 天没采动）` / `积压延迟 4.7 小时`），字段行不再重复写一遍。
- **值为 0 / 空的行整行省略**：`今日 任务 0 次`、`待内容采集 0`、`采集报错 空` 都不写；**不要写 `null` / `None` / `—` 给用户看**。
- **「共采集 N 篇 · 最晚发现 T」这一行必须有**（用户最关心这两个数）；`total==0` 写成「共采集 0 篇 · 尚未采集到任何文章」，「最晚发现」不要留空也不要编。
- 「最晚发现」指 `discovered_at`（**发现/入库时间**，不是发布时间）；监控台就这一个时间可用，不要拿 `published_at`（实测常为 `null`）顶替。
- **字段名固定写「采集开关 <开/关>」**，不要缩成「开关开/开关关」这类读不顺的写法（队列、频率也同理，别去头去尾）。
- **默认不给「近期文章」**：它和「最晚发现」重复，而且公众号长标题会撑爆 IM 消息。只在用户明确要看文章列表时列 2~3 条（日期 + 标题）。
- 已停摆号如果实测发现是**全站性问题**（`collector.online == false`），结论行末补上「（当前采集器离线，全站性）」，并在建议里明确「该号自身无异常」，不要让用户误以为要单独修这个号。

### 5.4 未命中 / 歧义

未命中：
```
【公众号查询】「<输入>」不在监控名单里
可能你要找的是：<候选A>（<状态>·<队列>）、<候选B>…
如确认，请用完整名字重发一次。
```

有歧义（多个同名候选）时列候选并要求指定，**不要替用户选**。

### 5.5 IM 压缩（飞书等）

压到 ~400 字以内：保留「结论 + 根因 + 采集开关 + 共采集/最晚发现 + 建议」，其余全砍。

## 6. 旁路：全站总览

用户问「采集是不是挂了 / 后台什么情况」而不是特指某个号时：

```bash
curl -sS -m 15 "$BASE/api/overview"
```

输出关键项：`collector.online` + `last_heartbeat_at`（离线多久）、`summary.collected_today` 与 `coverage_pct`、`summary.due_tasks` 与 `oldest_delay_label`、`summary.pending_usernames`（待补全标识存量）、`summary.bridge_online` / `resolver_online`，以及各 `queues` 的到期/最久延迟。

## 7. 硬性纪律

1. **只读**。任何 `POST/PUT/DELETE` 都不发；补标识、改队列、重跑任务都属于人的事，最多写进「建议」。
2. **不猜数**。所有数字必须来自接口返回；接口没给就不写。
3. **不翻页**。`page_size` ≤ 20。
4. **接口不可达就直说**，不要用历史印象或别的数据源兜。
5. 接口里能看到内网地址、队列权重等实现细节（如 `collector.config_json`）——**不要往外转发这些内容**，也不要写进给用户的回答里。
6. 结论先行：第一行必须是「公众号名 + 在不在名单 + 状态」。不要先讲你查了什么。
7. **本 skill 不包含任何脚本，也不需要在本地运行任何东西。** 所有查询用 `curl`（或任何 HTTP 客户端）直连 §1 的接口即可；不要去找、也不要依赖 `scripts/` 下的工具。
